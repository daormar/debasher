.. _concepts:

Programs, Processes and Options
===============================

This section names the pieces of a DeBasher program and says what each
one is, in words that hold whether the program is drawn in the web
interface or written as a module. The :ref:`webui` Section shows where
each piece is set in the editor, the :ref:`implem` Section how each is
written by hand, and the :ref:`exec` Section how a program is run from
the command line. Nothing here requires reading any code.

Programs and processes
----------------------

A **program** is a set of processes. A **process** is a Unix program:
a piece of code, in Bash, Python, R, Perl or Groovy, that is given its
inputs and the places for its outputs through named options, reads
the former and writes the latter, and ends. It does not know which
other processes exist, and it is the unit of reuse: the same process
can take part in many programs, and what changes from one program to
another is how its options are connected.

Every process has a name. A name may carry dot-separated qualifiers,
such as ``org.namespace.name``, which keep processes of different
modules from clashing when a program combines them.

A **module** is the file that holds a program: the processes, their
options and the connections between them. A module is written by hand,
in Bash, or generated by the web interface from a drawing, in which
case the drawing is the way to read and change it. Either way, the
module is what DeBasher runs, and a program built one way can be read
the other.

Options: the interface of a process
-----------------------------------

An **option** is a labeled value that a process receives when it runs,
such as ``-s`` or ``-outf``. The label says on which side of the
process the option sits: a label that starts with ``-out`` or ``--out``
names an **output**, where the process writes, and any other label an
**input**, which the process reads. The options of a process are its
whole interface: a process that runs alone, from the command line, is
given the same options that it is given inside a program.

Every option carries data of a **data type**: an int, a float, a
string, a file, a directory, or nothing at all for a flag, an input
that is present or absent.

An input gets its value from one of these places:

* the **command line** of the program, when a person gives it on each
  run; such an option can be mandatory or not;
* a **fixed value**, written into the program;
* the **specifications** of the process, such as its number of CPUs;
* the **output of another process**, which is what connects them (see
  below).

An option also has a **channel**, the way its data reaches the
process. The data can come as a **direct value**, the option holding
the data itself; as a path to a **file or directory** that the writing
process leaves under its output directory; as a **value descriptor**,
a small file where an output leaves a value for the processes that
read it; through a **FIFO**, a named pipe that the writer fills while
the reader drains it; or through a **shared directory**, into which
several processes write. The data type says what the data is, and the
channel says how it travels: a FIFO of type int carries one int per
line.

Connections and the dependency graph
------------------------------------

A **connection** joins an input of one process to an output of
another, or of the same one. An input takes a single connection, and
it then carries whatever the output carries, on the output's channel.
The connections of a program are its **dependency graph**: there is
no separate description of which process runs after which, since the
graph follows from the options alone, and DeBasher draws it, checks it
and schedules it before anything runs.

How a connection runs depends on the channel of the output:

* a connection through a file, a directory or a value descriptor makes
  the reading process wait until the writing process has finished;
* a connection through a FIFO runs both processes at the same time,
  the reader blocking until the writer sends and the writer blocking
  until the reader takes. DeBasher creates the FIFO under the output
  directory before the processes start, and a **mirror** tap of a FIFO
  shows what passes through it while a program runs.

A cycle made only of file connections is refused, since no process of
it could go first; a cycle through a FIFO is allowed, and is how two
processes talk back and forth. Where the graph cannot be read from the
options, as when a process reads a whole shared directory that other
processes fill, a process declares its dependency on another
explicitly.

Tasks: a process that runs many times
-------------------------------------

A process runs as one or more **tasks**. A **standard** process runs
once. An **array** runs one task for each element of a list, and a
**generator** one task for each index from zero up to a number that it
computes; in both, the options of each task are built from its
**task index**. A command line option that only decides how many tasks
a process has, such as a number of workers or a sample sheet whose
lines are counted, is a **task shaping** option: it shapes the tasks
and no task receives it.

Tasks connect to tasks. The task ``i`` of one process may read what
the task ``i`` of another produced, and then it waits for that task
only. A standard process that reads every task of an array or a
generator does so through a **fanout family**, one option whose label
ends in ``-ith`` and which stands for as many numbered options as
there are tasks; the family takes its count from a command line option
or from the number of tasks of the process at the other end. A family
can also go the other way, one output per task of an array that each
task reads.

The tasks of a process share its output directory. A task that needs a
place of its own asks for a **subdirectory** of it, which DeBasher
creates before the process runs and empties before the task runs, so
that the code of a process is the same whether it runs once or a
thousand times.

The output directory and the state of a run
-------------------------------------------

A program runs into an **output directory**, given when the run
starts. Every process has a directory of its own inside it, where its
outputs go, and DeBasher keeps its own bookkeeping beside them: the
options each process was given, its standard output, what the
scheduler reported, and a marker when it finished.

That bookkeeping is the **status** of each process, which is one of
``todo`` (not started), ``inprogress`` (running), ``finished``
(completed), ``unfinished`` (did not complete), and
``unfinished_but_runnable`` (did not complete, is not running, and can
be run again). A program run again into the same output directory
**resumes**: it runs the processes, or the tasks of an array, that did
not finish, and leaves alone those that did. A process may declare in
its own code that it can be **skipped** on a run, which counts as
finished, or be marked to run on every run.

Schedulers, resources and environments
--------------------------------------

A **scheduler** decides when each process runs. The **built-in**
scheduler runs a program on one machine, fitting processes into its
CPUs and memory; **Slurm** sends each process to a cluster as a job,
and an array as a job array. A program that uses FIFOs runs with the
built-in scheduler, since both ends of a FIFO have to be on the same
machine. Every process carries **specifications**: the CPUs, memory
and time it needs, and, under Slurm, the partition, account or nodes;
a cap on how many of its tasks run at once; and, in a general program,
its explicit dependencies.

A process may name a **Conda environment**, which DeBasher creates
and activates for it, or a **Docker image**, in which it runs, so that
the program carries what each process needs.

Steps and sequential processes
------------------------------

The dependency graph is fixed before a program runs, but some
processes only know what to run next while they run: a loop that
sends each value it reads to one of two transformations, for instance.
Such a process runs its stages itself, as **steps**, and a stage whose
code is not Bash, or which is to run on Slurm with resources of its
own, is declared as a **sequential process**.

Two kinds of program
--------------------

A **general program** processes a batch of inputs: every process runs
its tasks as soon as what they read is ready, and the program ends
when the last one has finished. A **resident program** processes a
stream: its processes, called **nodes**, keep a state of their own and
run until told to stop. Nodes exchange **messages**, one line of JSON
each, through FIFOs, which are their **ports** and **channels**; a
node acts only in reaction to a message, and the activity of a program
starts with a message written into it from outside, on an
**external port**. A node that crashes is relaunched and returns to
the state it had, from its last **checkpoint** and the **input log**
of what it received since; a **snapshot** takes a consistent
checkpoint of every node at once, and a **Supervisor** watches the
nodes, relaunches the ones that go down and relays the orders to
snapshot or stop. A node may also launch a general program for each
request it receives, so that a stream drives batch runs. A resident
program runs with the built-in scheduler, and its nodes are written
in Python.

Both kinds define their processes the same way, with the options and
connections above; the :ref:`resident` Section says what a node adds.
